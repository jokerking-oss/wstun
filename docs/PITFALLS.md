# 踩坑记录

这里记的都是**真踩过的坑**，不是推测。每条都付出了调试代价，写下来是为了别人不用再付一遍。

---

## 一、协议层

### 1. 明文 CONNECT 直连住宅代理 = 白搭

最早的想法很自然：既然住宅代理不限目的地，那直接把系统代理指向它不就行了？

不行。住宅代理的客户端侧是**明文 HTTP 代理协议**，`CONNECT chatgpt.com:443` 这个请求行把目标 FQDN 完整暴露在路径上。中间盒基于 SNI / HTTP 特征做 RST 注入，连接在 TLS 握手阶段就被重置。

实测十个主流目标逐个发起 `CONNECT`，代理侧**全部返回 200**（说明它自己不挑目的地），但**六个在 TLS ClientHello 阶段被 reset**。

结论：问题的本质不是出口的信誉或带宽，而是**域名的暴露时序**。必须让 SNI 第一次出现在线路上的位置在境外。这也直接决定了配置里的 `fallback` **必须保持为空** —— 任何"明文直连住宅代理"的降级路径都是自欺欺人。

### 2. `*.workers.dev` 被整段屏蔽，改用 `*.pages.dev`

初始入口选了 Cloudflare Workers 的默认域名，结果整段不可达。换成 Pages 的 `*.pages.dev` 后正常。

这类"整段域名被屏蔽"和单点 IP 封锁不同，换 IP 没用，只能换**域名空间**。多准备几种部署形态（`server/` 下有四套）是有意义的。

### 3. WSS 通道的固定成本是 1.13 秒

拆开看：

- TCP 三次握手 → 1 RTT
- TLS 握手 → 1 RTT（TLS 1.2 是 2 RTT）
- HTTP/1.1 `101 Switching Protocols` 的 Upgrade 往返 → 1 RTT

合计约 1.13 秒。单个请求感知不到，但一个网页几十个跨域资源就是**逐次重复缴纳**。

**"网页慢"经常不是带宽问题，是 RTT 累积 × 连接数的乘积。** 先做归因，别猜。

### 4. `getaddrinfo` 的顺序阻塞会白等 21 秒

系统解析域名拿到多个候选地址后，默认**按顺序阻塞式尝试第一个**。如果第一个恰好丢包，就要吃满系统超时才轮到下一个 —— 观感就是"网络卡死"，实际是**在傻等**。

改成：已验证的好 IP 优先、每个候选 4 秒硬超时、失败立刻切下一个（Happy-Eyeballs 的简化实现），并把好 IP 集合**持久化落盘**，冷启动直接命中。

### 5. Nagle 与 Delayed ACK 的交互惩罚

默认 Nagle 算法会对小包做约 40ms 的攒批。对 TLS 握手这种一问一答的序列是纯亏损。置 `TCP_NODELAY`。

单看只有 40ms，但握手是 3 个 RTT，叠加起来就不可忽略了。

## 二、WebRTC 泄露（这块坑最多）

### 6. 泄露是真的，而且根因只有一个

检测报告给出了一个本机所在地的 IP。默认假设应该是"误报"，但**不能接受假设**，要做反证。

直连三个独立的 IP 回显端点，取到本机真实出口 —— 与报告里那个 IP **落在同一个 /24**。这不是噪声，是确凿的 host / srflx candidate 泄露。

根因：**WebRTC 的 ICE 候选走 UDP，而系统代理（WinINET / WinHTTP 层）只代理 TCP。** UDP 直接绕过代理栈从物理网卡出去，把 NAT 映射后的公网地址交给对端。

顺带解释了报告里另一条"出口国家不一致" —— **同一个根因，两个症状**，不是两个独立缺陷。找到根因就能一次修干净。

### 7. Edge 和 Chrome 的策略名不通用

封堵方案是下发 Chromium 的 `disable_non_proxied_udp`。陷阱在于**键名在 Edge 与 Chrome 的命名空间里不一样**：

- Edge → `WebRtcLocalhostIpHandling`
- Chrome → `WebRtcIPHandlingPolicy`

**键名差一个词，策略静默失效** —— 不报错、不打日志、不产生任何可观测信号。你只会以为"设了但没用"。类型也必须是 `REG_SZ`，写成 DWORD 同样静默失效。

### 8. `Software\Policies` 的 DACL 会把你自己挡在门外

该键被系统加固：

```
NT AUTHORITY\SYSTEM         Allow  FullControl
BUILTIN\Administrators      Allow  FullControl
<你的账户>                  Allow  ReadKey     ← 只有读权限
```

也就是说**普通完整性级别下连账户所有者自己都写不进去**，首次尝试直接 `WinError 5`。

只能做自提权入口：`ShellExecute runas` 触发 Consent UI。脚本内需要一个可靠的方式判断"当前是否已提权"，可用 `cacls %SYSTEMROOT%\system32\config\system` 反查 —— 这个路径普通权限读不了。

### 9. 受限令牌（restricted token）会让权限判断完全反向

最反直觉的一环：第一次判定"当前用户是否属于管理员组"，结论是**否**。如果就此采信，整个方案方向都会跑偏。

复核发现真正原因是：**判定进程本身处于受限令牌状态，管理员 SID 被过滤**，所以它看任何人都"不是管理员"。

改用 `Get-LocalGroupMember -SID S-1-5-32-544` 与 `Win32_GroupUser` CIM 双路交叉验证，确认账户确实在 Administrators 组。

**结论：在受限 / 沙箱环境下，`IsInRole(Administrator)` 是负可信信号，不能作为权限判定依据。**

### 10. 策略是 `Dynamic Policy Refresh: No`，只能靠重启浏览器生效

该策略不热加载。判断它是否生效，唯一可靠的方法是**时序比对**：

- 注册表键的 `LastWriteTime`
- vs 浏览器**本体**进程的创建时间（`GetProcessTimes` 取 CreationTime FILETIME）

用的是进程创建时间，**不是**任务管理器里的进程数量。

这里还埋着第二个坑：`msedgewebview2.exe` 是系统组件、长期驻留，创建时间可能在两天前。如果按进程名前缀 `msedge` 模糊统计，就会误判成"浏览器没重启"。必须精确区分浏览器本体与 WebView2 运行时。

## 三、架构与配置

### 11. 凭证在边缘，不在客户端

换住宅代理时才发现：`host / port / user / pass` 是作为常量编译进**边缘节点**的（现已改为环境变量注入）。只改本地 `wstun.json` 完全无效，出口不变。

所以完整链路是：**改边缘配置 → 重新部署边缘 → 重启隧道 → 出口自检**。少一步都不行。

### 12. fail-closed 的取舍

住宅路径不可达时，允许静默降级到边缘节点的机房出口，是个**看起来很合理、实际很危险**的设计。

一旦回落，流量会在你不知情的情况下被 ASN 分类器打上 `datacenter` / `proxy` 标签，造成**污染且不可回溯**。

所以 `strict_residential: true` 会物理切断一切 direct 通路（路由函数永远返回住宅路径，连底层连接函数也不允许建 direct 连接）。这是典型的 fail-closed：**代价是可见的失败，收益是不可见的一致性。**

### 13. 守护状态机的收敛窗口（关键细节）

如果简单地"探测失败就计一次失败"，那么采样间隔取小就会把**正常启动过程**误判成故障，白切一次代理。

正确做法：**只有"拉起 + 等满 45 秒收敛窗口后仍不可用"才递增失败计数。**

有了这个窗口，采样间隔就可以取到 6 秒 —— 只影响"发现"的延迟，不产生假阳性。断网最多 6 秒被救回。

另外两个必备件：
- **单实例文件锁**，避免重复拉起；
- **用户意图标记** —— 用户手动关掉的，守护不抢。防止守护与人工操作产生竞态。

## 四、Windows 工具链

| 坑 | 现状 |
|---|---|
| `wmic` | 已被微软移除，调用直接 `FileNotFoundError`。改用 `tasklist /FO CSV` 或 CIM |
| `sc.exe` | 存在于程序黑名单，查服务一律被拦。改读注册表 `HKLM\SYSTEM\CurrentControlSet\Services` |
| 从 Bash 调 PowerShell | 被安全策略拒绝（bypasses PowerShell security checks）。改用原生 PS 调用 |
| PowerShell stdout 不回传 | 某些环境下 stdout 静默丢失。改用"**写文件 → 读文件**"的中转模式 |
| 批处理中文乱码 | `.bat` 必须用 GBK / CP936 写入；`.vbs` 同理。UTF-8 会满屏乱码 |
| 沙箱对 `shutil.rmtree` 的钩子 | 对含大量子项的目录会报 `Some operations were aborted`。改用 `SHFileOperationW` + `FOF_ALLOWUNDO`，逐项送回收站，顺便获得可还原性 |

## 五、边缘入口优选、长任务与性能归因（"延迟低 ≠ 快"）

背景：隧道段的瓶颈是「中国 → Cloudflare 边缘」。Cloudflare 是 Anycast，同一个域名会解析到
多个边缘 IP，而**不同 IP 从国内走的国际路由差别巨大**。DNS 返哪两个是随机的，默认拿到的未必好。

### 14. 延迟排名第一的 IP，吞吐只排第四

`pick_ip.py` 用 TCP/TLS 握手延迟排名，第一是 `104.17.176.26`（190ms）。但真实吞吐测试里
它只排第四（5.81 MB/s），而延迟排第五的 `104.17.104.45`（328ms/131ms）以 **6.43 MB/s** 居首。

**握手延迟衡量的是 RTT，吞吐衡量的是路径带宽与拥塞 —— 两者不相关。** 做优选**必须实测吞吐**，
不能只看 ping。

### 15. 并发测速会互相抢带宽，把结果污染得面目全非

第一轮我用 4 并发跑 8MB 拉取，原 IP 测出 **0.54 MB/s** —— 而串行复测同一 IP 是 **3.46 MB/s**。
因为多个大流共享同一条国际链路，谁先谁后、谁插队全看运气。

**测吞吐必须串行（`--workers 1`）。** 并发只能用来筛"能不能通"，不能用来排名。

### 16. 连发太多请求会被测速端点限流

并发跑完 9 个 8MB 拉取后，`speed.cloudflare.com` 对后续请求一律返回 **403**，过一会儿自动恢复。
所以候选不要一次丢太多；另外注意 **`__down?bytes=` 参数过大也会 403**（12MB 就触发了）。

### 17. 优选结果会被一行代码悄悄忽略（最容易漏的坑）

客户端原有的逻辑是：

```python
good = _GOODIP.get(host)
if good in addrs:        # ← 要求记住的 IP 必须出现在 DNS 结果里
    addrs.remove(good)
    addrs.insert(0, good)
```

而优选出来的 IP **恰恰通常不在当前 DNS 返回里** —— 这正是它有价值的原因。于是优选出来的 IP
永远轮不到，`pick_ip.py --apply` 写了半天也毫无效果，且**完全静默**。

改成只要记过就优先试，连不上在 `per_ip`（默认 4s）后自动回退 DNS 列表：

```python
good = _GOODIP.get(host)
if good:
    if good in addrs:
        addrs.remove(good)
    addrs.insert(0, good)
```

连上后 `_save_goodip()` 会把该 IP 回写，所以优选结果是**自我固化**的。

**通用教训**：任何"外部注入优化参数"的机制，都要检查消费端有没有隐含的准入条件
（这里是 `in addrs`）把注入值静默过滤掉。

### 18. 写入的配置会被**运行中的进程**静默覆盖回去

改完第 17 条、把优选 IP 写进 `client/goodip.json` 之后，过了几分钟再一看 —— **又变回旧值了**。

原因是：正在运行的客户端进程在内存里持有 `_GOODIP` 字典，而 `connect_fast` **每次连接成功都会调
`_save_goodip()` 把整个文件重写一遍**。所以文件虽然被外部改过，进程下一次建连就把它覆盖回去了：

```
写入 104.17.104.45  →  几分钟后  →  又变回 172.66.44.191
```

**全程不报任何错，没有任何日志。** 只有对着 mtime 看才能发现（`goodip.json 最后修改: 07:57:22`，
而"现在"是 07:57:24 —— 两秒前刚被重写）。

正确顺序是**停进程 → 写文件 → 起进程**：

```bat
python tools\pick_speed.py --workers 1 --ips "1.2.3.4,5.6.7.8"   :: 实测吞吐
python tools\apply_goodip.py --status                            :: 看状态
python tools\apply_goodip.py <边缘IP> --restart                  :: 停守护→停隧道→写→起隧道→起守护
```

**还有个连带坑**：如果那个"看门"的守护进程在跑，它会发现端口没了、**立刻把客户端拉起来** ——
起来的进程读到的还是旧文件。所以必须**先停守护**，再停客户端，最后才写文件。

**先把文件分成两类**（本项目的实际划分，照着读 `client/wstun.py` 第 16–20 行即可确认）：

| 文件 | 语义 | 外部编辑后 |
|---|---|---|
| `client/wstun.json` | **只读**，启动时 `json.load` 一次，全程不回写 | 必须重启才生效，但**不会被覆盖** |
| `client/goodip.json` | **读写**，`connect_fast` 每次成功建连都 `_save_goodip()` | **必须「停→写→起」**，否则几分钟内被静默覆盖 |
| `client/direct_fail.json` | **读写**，走 CF 直连失败的域名缓存（6h TTL） | 同上 |

把两类搞混的代价是对称的：改只读文件后**不重启**是白改，改读写文件后**不重启**是白改一半
（会被回滚）。

**通用教训**："配置文件"不等于"生效状态"。只要有一个长驻进程把它读进内存后又回写，
外部编辑就是**竞态**。要么做成一次性读取、要么让工具自己处理停止/启动的顺序，
要么在写入前检测进程是否在跑并**拒绝执行**（本项目选了第三种，退出码 3 并打印正确做法）。

### 19. 长任务想"脱离调用方独立跑完"，普通的 detach 是不够的

"停隧道 → 写配置 → 起隧道"这条流程有个自指困境：**发起这次操作的进程自己也在用这条隧道**。
隧道一停，它的网络请求立刻失败。而且它还活不过调用结束 —— 实测用
`subprocess.Popen(creationflags=DETACHED_PROCESS | NEW_PROCESS_GROUP)` 启动的脚本，
**在发起调用返回的瞬间就被连带杀掉了**：日志只留下一行启动横幅，系统状态零变化。

两个要点：

1. **进程必须真正脱离调用方的 Job Object。** 可行做法是用 **WMI** 创建进程
   （`Invoke-CimMethod -ClassName Win32_Process -MethodName Create`）—— 它的父进程是
   `WmiPrvSE.exe`，由系统服务托管，调用方结束甚至断链都影响不到它。
   ⚠️ 代价：WMI 创建的进程**没有 stdout**，脚本必须**自己写日志文件**。
   ```bat
   python tools\spawn_detached.py tools\apply_wide.py --ip <边缘IP> --grace 5
   ```
2. **在停隧道之前，先把系统代理临时设为「直连」。** 如果发起方访问的是国内域名，
   直连可达 —— 于是这段窗口它不会失联；隧道起来后立刻恢复代理，全程 `try/finally` 兜底。

**验证 detach 是否真的成功的方法**：让探针写下 "起 / +6s / +12s" 三行不同时间戳的内容，
**跨两次独立的工具调用**去读 —— 三行都在，才算真的脱离了进程树。

### 20. 提速要归因到"哪一段"，而且**测量点必须靠近被测段**

换完边缘 IP，**裸路径吞吐从 4.3 涨到 6.4 MB/s，但隧道内只从 3.5 涨到 3.9**。如果不做归因，
很容易继续在"换更快的 IP"上打转。

**第一轮归因（结论是错的）：**

1. 是计算瓶颈吗？满速下载时看进程 CPU —— 只占 **14% 单核**，排除。
2. 是并发度不够吗？并发 1 / 4 / 8 的聚合是 **1.93 / 3.21 / 3.86 MB/s**，已近平台期，排除。
3. 是哪一段？**从本机直连住宅代理只有 1.26–1.77 MB/s（4 并发 2.09）**，而隧道能跑到 3.86 → 于是
   我判定"瓶颈在上游住宅线路"。

**这一步推错了，而且错得很典型。** 我从中国直连美国住宅代理测出的数字，**度量的是"中国↔美国链路"，
不是住宅代理的能力** —— 中间任何一段烂链路都会冒充成被测段的"上限"。

**第二轮归因（换成从离被测段最近的一端发起）：**

让**边缘节点**（就在美国境内）去测"边缘 → 住宅 → 目标"这一跳，用的是同一个 worker 的
`?upspeed=N` 端点：

```
住宅腿，从边缘侧测：单条 5 MB/s，16 并发聚合 38.64 MB/s
```

**住宅腿根本不是瓶颈。** 真正的天花板是「客户端 → 边缘」这段**跨国链路**（≈6 MB/s），
而隧道已吃到其中约 **73%**。

**两条通用教训：**

- **测某一段的容量，必须从离它最近的那一端发起。** 否则你测到的是"发起端到被测段之间的整条链"，
  不是被测段本身 —— 会把远端的问题误判成近端的问题。
- **归因的每一步都要问"这个数字度量的是什么"**，而不是"这个数字是多少"。第一轮里每个数字都是
  真实测出来的，但第 3 步那个数字**度量的对象错了**，结论就整个反了。

结论：**速度由最慢的一段决定**，所以要先把每一段量准（且用对的测量点），再决定动哪一段。

### 21. 连接池要开够：它决定的是"哪部分流量享受了优化"

连接池预热做好了，并不代表**所有**连接都享受到了。第一版 `pool.up = 6` —— 恰好等于浏览器
**每个域名**的并发连接上限，而一个普通页面经常跨 2–4 个域名，于是**超出的连接全部退化成现场握手**，
把前面所有优化又白送回去。

| 场景 | 建连耗时 |
|---|---|
| 池未命中（现场 TCP + TLS + Upgrade） | **884 ms** |
| 池命中（直接取走预热好的通道） | **5 ms** |
| 调大 `pool.up` 6 → 12 后的端到端 TTFB | 1562 ms → **681 ms** |

**关键是先确认"预热贵不贵"**：读代码发现预热**只建到边缘的 WSS，不触发上游拨号**
（上游是在请求到达时才按需连的）—— 所以加池子**不占用任何上游会话、近乎零成本**，
可以放心"宁可开大"。

**通用教训**：一个"减少固定开销"的优化，**覆盖面**和**单次收益**同样重要。写代码时顺手问一句
"这个优化对哪部分流量有效？剩下的那部分呢？" —— 否则会出现"优化做了，但只有 1/3 的请求吃到"。
